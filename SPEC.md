# Yardhand spec (0.3)

Yardhand is a file-based issue tracker that lives in a repo. Status is a folder, an issue is a folder, and the rules are mechanical so a script or a model can follow them. This file is the source of truth. Code and tests follow it.

The files are the source of truth for the issues. The CLI is the main tool for developers and models, but every rule here can be followed by hand with a text editor and a file manager, and AI is optional. CI can run `validate` on every push (see `init`), so mistakes are caught however a change was made.

## Layout

```
issues/
  yardhand.json
  backlog/
    017-add-auth/
      ISSUE.md
      notes.md
  ready/
  in-progress/
  done/
```

- `issues/` is at the repo root (not `.issues/`: search tools and agents skip dot-folders). `yardhand.json` lives inside it.
- Each status in `yardhand.json` has a folder of the same name.
- Each issue is a folder named `<id>-<slug>/`, or `<id>-bug-<slug>/` for a bug, that contains `ISSUE.md` and any reference files.
- `issues/ROADMAP.md` (generated) and `issues/releases/<version>.md` (generated by `release`) are the only other things `issues/` may hold.
- Reference files inside an issue use relative paths or the issue ID. Never hardcode `issues/<status>/...`.
- `issues/` must never ship in a published package, a container image, or a live site. Deploy from a build output folder, never the repo root.

## yardhand.json

```json
{
  "statuses": ["backlog", "ready", "in-progress", "done"],
  "labels": ["backend", "frontend"],
  "assignees": {
    "@ryan": "person",
    "@claude-opus": { "type": "model", "run": "claude -p --model opus \"Build {{issue}}\"" }
  },
  "agents": ["claude-code", "codex"]
}
```

- `statuses` is an ordered list. It is the only source of truth for which statuses exist.
- The first status is where new issues start.
- `backlog` and `done` are required. Neither has to be first or last: any status can sit before `backlog` (for example `triage`) or after `done` (for example `canceled`).
- Status names are lowercase kebab-case: `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`. The interactive commands accept free-form names and normalize them (see "Names typed by people"); the file itself is strict.
- Names are unique. `releases` is reserved and cannot be a status.
- `backlog` means unrefined, `ready` means refined and safe to build, `in-progress` means claimed. `ready` is not required, but the "Picking up work" convention assumes it.
- `labels`: optional list of allowed label names, lowercase kebab-case, unique. Missing means none.
- `assignees`: optional map of handle to `"person"` or `"model"`, or to an object `{ "type": "person" | "model", "run": "<command template>" }`. Handles are `@` plus lowercase kebab-case: `^@[a-z][a-z0-9]*(-[a-z0-9]+)*$` (no dots: `@gpt-6-1-sol`). `run` is kept for a future `run` command and is not used yet. Missing means none.
- `agents`: the AI tools that work in this repo, any of `claude-code`, `codex`, `opencode`, `other` (any tool that reads `AGENTS.md` or `.agents/skills`). `[]` means AI is off. Missing (a config from before 0.4) means AI is on with `AGENTS.md` only. Set by `init`; to change it, edit the list and run `yardhand init --force`. See "AI tools".
- `labels`, `assignees` and `agents` are edited by hand. No emails, here or in issues.

## IDs

- Three levels at most: `017`, `017.01`, `017.01.01`.
- Level 1 is three digits. Levels 2 and 3 are two digits and start at `01`. Regex: `^\d{3}(\.(0[1-9]|[1-9]\d)){0,2}$`.
- No zero segments below level 1. `017` is valid, `017.00` and `017.00.00` are not.
- `000` is the catch-all for maintenance and bugs with no clear home. It is a normal level-1 ID.
- IDs are permanent and never reused, including after an issue is done.
- Allocation: scan every status folder. The next level-1 ID is the highest existing level-1 number plus one. The next child of a parent is the highest existing child number of that parent plus one. Level-1 numbers go up to 999, children up to 99. Allocation fails when full.
- The scan matches on separators: folder name must start with the ID followed by `-` (`017-`). Never match by prefix alone, so `017` never matches `0170`.
- Nobody invents IDs. With the CLI, `yardhand new` allocates them. Without it, follow the allocation rule above exactly.

## Slugs and the `bug-` prefix

- Lowercase kebab-case, verb first, for example `add-auth`.
- Regex: `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`.
- Slugs may change. The ID is the key. A rename changes the folder name only.
- `bug-` is the only reserved prefix. It appears only right after the ID and means `kind: bug`. After it, describe the symptom (`bug-login-redirect-loop`). `fix-` is not reserved. No other slug may start with `bug-`.
- The tool adds the prefix. Priority, size, labels, assignee and effort are not in the folder name, so changing them never renames a folder.
- A slug longer than 40 characters (not counting `bug-`) is a warning.

## Names typed by people

`init` (custom statuses), `new` (the slug), `move` and `list` (status names) normalize what is typed: trim, lowercase, and turn spaces and underscores into a dash. `Review 1` becomes `review-1`, and the result is shown. What is stored on disk is always the strict form.

## ISSUE.md

```
---
# Required
id: 017.01.01
kind: task          # feature | task | bug
parent: 017.01      # omit for level 1 only
status: backlog     # must match the folder

# Optional (blank = unset)
priority:           # urgent | high | medium | low
size:               # small | medium | large
labels:             # names from issues/yardhand.json, e.g. [backend, auth]
depends-on:         # issue IDs, e.g. [017.01.01, 017.02]
related:            # issue IDs
assignee:           # "@handle" from issues/yardhand.json, e.g. "@claude-opus"
effort:             # free text, one word, e.g. low | medium | high | xhigh
released-in:        # set by `release`
---

# Build login form

## Description
<!-- What and why. A buildable unit should fit one model session. -->

## Acceptance criteria
<!-- Checkable outcomes, one per line, as checkboxes: - [ ] ... -->
- [ ]
```

- `id`: required. Must equal the ID in the folder name.
- `kind`: required: `feature`, `task` or `bug`. `new` defaults to `feature` at level 1 and `task` below. `kind: bug` and the `bug-` folder prefix must agree.
- `parent`: required for levels 2 and 3 and must be the ID with its last segment removed. Omitted for level 1. See "Moving work to a different parent" for the one exception.
- `status`: required. Must equal the name of the status folder the issue is in.
- `priority`: optional. One of `urgent`, `high`, `medium`, `low`. Front matter only; never part of the folder name.
- `size`: optional. One of `small` (a few files, under half a session), `medium` (a normal session), `large` (barely fits one session; consider splitting). Meant for issues with no children.
- `labels`: optional list of label names, each listed in `yardhand.json`, no repeats.
- `depends-on`: optional list of issue IDs that must be finished first, for example `[017.02, 017.03]`. The link is stored on the dependent issue only; there is no reverse field. A `depends-on` loop (A needs B and B needs A) is an error.
- `related`: optional list of issue IDs that are linked but do not block this issue. Related links may point both ways.
- `assignee`: optional. A handle listed under `assignees` in `yardhand.json`, written in quotes (`assignee: "@claude-opus"`) because YAML cannot start a value with `@`. People and models use the same form.
- `effort`: optional. How hard the assigned model should think, in that model's own words. Free text, but one word: `^[a-z0-9][a-z0-9-]*$` (it may be passed into a shell command).
- `released-in`: optional semver (the grammar at semver.org: no leading zeros, no empty identifiers), set by `yardhand release` when shipped.
- Blank means unset for every optional field. The template writes them all, blank. Only `parent` is omitted, for level 1, and `effort` when AI is off (`"agents": []`) and no effort was given. A missing optional field means the same as a blank one; `set` adds it when needed.
- Lists are written `[a, b]`. The 0.2 form (`a, b`) is still read. Command flags take comma-separated values.
- The `# Required` and `# Optional (blank = unset)` lines and the comment after each field are for people editing by hand. `validate` does not check them or the field order. Every command that edits front matter (`set`, `move`, `release`) changes only the value on the matching line and keeps its comment in the same column.
- The body starts with an H1 title, seeded by `new` from the slug without `bug-`, in sentence case (`add-login-form` becomes `Add login form`). It can be edited freely and is never checked against the slug.
- Acceptance criteria are checkboxes, one per outcome. An empty `- [ ]` is a placeholder, not a criterion.
- Front matter is a simple `key: value` block between `---` lines. A comment starts with `#` at the start of a line or of a value, or after whitespace; a `#` inside a word is part of the value. Matching surrounding quotes are taken off a value. No nesting. A key may appear only once. Both LF and CRLF line endings are accepted.

### Moving work to a different parent

The folder name and ID never change. Update `parent:` to the new parent. `parent:` is the source of truth for rollup, so after such a move it may differ from the ID prefix. `validate` accepts a different `parent` only if that parent exists.

## Commands

All commands, `init` included, run from the repo root or any folder below it. Yardhand finds `issues/yardhand.json` by walking upward. `init` in an already-initialized repo fails (even from a subfolder), and with `--force` it works on the existing root.

`new`, `move`, `set`, `roadmap`, `release` and `init` take an exclusive lock (`issues/.yardhand-lock`, a folder created atomically that holds the owner's process ID and a random token), so concurrent runs cannot allocate the same ID. A lock is abandoned only when the process that took it is no longer running, or, if it never wrote an owner, after 2 seconds. A slow but live holder is never evicted, however long it holds. Removing an abandoned lock is serialized by a second short-lived mutex (`issues/.yardhand-lock.reclaim`). Under it, the lock is re-read and removed only if it is still the same lock (same token) and its owner is still gone; while a lock folder exists nobody else can create one, so this cannot race with a new holder. A reclaim mutex older than 5 seconds belongs to a reclaimer that died and is cleared. A lock is released only by its owner, and a failure to remove it never hides the result of the work. A command waits up to 10 seconds for the lock (override with `YARDHAND_LOCK_TIMEOUT_MS`), then fails with a message. Folders under `issues/` that start with `.` are tool internals and are ignored.

`new`, `move`, `set`, `release` and `init` first need a complete view of every existing ID, so they refuse to run when: a status path is a file or cannot be listed; any entry cannot be inspected (permissions or I/O errors are never read as "absent"); a folder under `issues/` that is not a status holds, or may hold, issue folders; or there are symlinks. Yardhand never follows symlinks: `issues/` itself, status folders, issue folders, and `ISSUE.md` are checked. Reference files inside an issue folder are the user's and are not inspected.

`move` and `set` (and `release`, which never moves a folder) write the new `ISSUE.md` to a temp file in the issue folder first (a random name, `.ISSUE.md.<random>.tmp`, created exclusively, so nothing at a guessable path is ever written through), so a failed or partial write can only damage the temp file. If the folder has to move (a status change, or a `kind` change that adds or removes `bug-`), it then renames the folder, and renames the temp file over `ISSUE.md` (an atomic replace). If that last step fails, it renames the folder back, so the folder and the fields never disagree. The cases it cannot repair are a failure of the move-back itself, which it reports with exactly what state the issue is in, and a crash between the two renames, which leaves a status mismatch plus a temp file. `validate` reports both, and the temp file's message says how to finish or undo the change. If the status folder is missing, `move` creates it.

### `yardhand init`

Interactive by default, in a terminal:

1. **Pick statuses.** A space-bar checklist: `triage`, `ready` (pre-checked), `in-progress` (pre-checked), `review`, `merge-ready`, `blocked`, `canceled`, and "Add custom statuses...". `backlog` and `done` are always included. (`ready` replaced `todo` in 0.3.0.)
2. **Custom statuses** (only if chosen). Free-form names separated by commas (semicolons also work), normalized (`Review 1` becomes `review-1`), shown as `Creating: ...`. Empty names, duplicates, `backlog`, `done`, `releases` and names with other characters are rejected.
3. **Order** (always shown, so the team sets the order). A numbered list; nothing is pinned. Up/Down moves the cursor, space grabs or drops a status, while grabbed Up/Down moves it and a digit key (1-9) jumps it to that slot, Enter confirms. The starting order is `triage`, `backlog`, `ready`, `in-progress`, `review`, `merge-ready`, `blocked`, `done`, `canceled`, then custom statuses in the order typed.
4. **AI tools.** A checklist: "Which AI tools will work in this repo?" with Claude Code, Codex, OpenCode, and "Other (reads AGENTS.md or .agents/skills)". Pre-checked: the `agents` already in `yardhand.json`, else the tools whose files are in the repo (`CLAUDE.md` or `.claude/` for Claude Code, `.codex/` for Codex, `.opencode/` or `opencode.json` for OpenCode, and Other when only `AGENTS.md` or `.agents/` is there). Picking none turns AI off. See "AI tools".
5. **Ignore entries** (only if `.npmignore` or `.dockerignore` exists at the root without an `issues/` line). Asks `Add issues/ to ... so it never ships in a package or image?`, default yes.
6. **CI check** (only in a git repo without `.github/workflows/yardhand.yml`). Asks `Add a GitHub Action that runs yardhand validate on every push?`, default yes.
7. **Create** everything and print the final order and what was created.

Non-interactive: `yardhand init --yes [--statuses a,b,c] [--agents a,b|none] [--no-ignore] [--no-ci]`. Defaults to `backlog,ready,in-progress,done`. `--statuses` is taken as the order and must already be valid (no normalization). `--agents` takes `claude-code`, `codex`, `opencode`, `other`, or `none` to turn AI off; without it, `init` uses the `agents` already in `yardhand.json`, else the tools found in the repo, else `other` (the `AGENTS.md` block only, as before 0.4). Steps 5 and 6 default to yes; `--no-ignore` and `--no-ci` skip them.

Ignore entries are append-only: one `issues/` line at the end of each existing file that lacks one. `init` never creates those files, never edits other lines, and never touches `.gitignore` (issues stay committed). The workflow is created exclusively and never overwritten:

```yaml
name: yardhand
on: [push, pull_request]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npx --yes yardhand@<version> validate
```

`<version>` is the version that ran `init`, so CI never changes behavior on its own.

Creates `issues/`, `issues/yardhand.json` (with empty `labels` and `assignees`), and one folder per status (with a `.gitkeep` in each empty one). Creates the catch-all `000-maintain-repo` issue in `backlog` (even when another status comes first) when no `000` issue exists, so `000.NN` children (maintenance, bugs with no clear home) have a parent. Its description explains its use, says it is never moved to `done`, and it has no checkboxes. Writes the AI files for the chosen tools (see "AI tools"). Prints no suggestions for other tools. Refuses to overwrite an existing `yardhand.json` unless `--force`; with `--force` it replaces the statuses and keeps the labels and assignees (and the agents, unless `--agents` or the checklist says otherwise). It takes the same lock as `new` and `move`, and runs the same completeness check, so a status list that omits a folder holding issues, or a tree it cannot fully read, is refused before anything is written. The catch-all is created with exclusive operations and is never overwritten. If `issues/` exists but cannot be read, `init` fails; it only starts fresh when nothing is set up. It validates `--statuses` even when it is empty.

### `yardhand new <slug> [--parent <id>] [--kind feature|task|bug] [--priority urgent|high|medium|low] [--size small|medium|large] [--labels <names>] [--depends-on <ids>] [--related <ids>] [--assignee @handle] [--effort <word>]`

Allocates the next ID, creates `issues/<first-status>/<id>-[bug-]<slug>/ISSUE.md` from the template, and prints the ID, the path, and a summary line (kind, priority, parent, status). The slug is normalized. A leading `bug-` in the slug becomes `--kind bug`, and the output says so; it fails if `--kind` says otherwise. Without `--kind`, level 1 is a `feature` and deeper levels are `task`. With no `--parent` it creates a level-1 issue. Fails if the parent does not exist or the parent is already level 3. `--depends-on` and `--related` take comma-separated IDs, and every ID must already exist. `--labels` takes comma-separated names, each listed in `yardhand.json`. `--assignee` must be a handle listed in `yardhand.json`; a missing `@` is added and the output says so. `--effort` must be one word; with no assignee, or a person, the issue is still created and a warning is printed to stderr. `new` builds the issue folder under a temporary `.new-*.tmp` name and renames it into place, so a failed `new` leaves nothing behind.

### `yardhand move <id> <status>`

Moves the issue folder to the status folder and rewrites `status:` in `ISSUE.md`. The status name is normalized. Fails if the status is not in `yardhand.json`, the ID is not found, or the destination already holds a folder with that name. Moving to the current status changes nothing and succeeds. Children (by `parent:`) are never moved; the output lists them. The folder name, `bug-` prefix included, is kept.

### `yardhand set <id> [--kind ...] [--priority ...|none] [--size small|medium|large|none] [--labels <names>|none] [--parent <id>] [--depends-on <ids>|none] [--related <ids>|none] [--assignee @handle|none] [--effort <word>|none] [--released-in <semver>|none]`

Changes fields on an existing issue. Values are checked the same way as in `new`; a field an older file lacks is added before the closing `---`. The same effort warning applies after the change. At least one flag is required. A value replaces the old one and `none` clears the field. `id` and `status` cannot be set (use `move`). Every change is validated before anything is written: IDs must exist, `parent` must be shallower than the issue (and a level-1 issue has none), `depends-on` cannot create a loop, `released-in` must be semver. Passing `--kind` also makes the folder name agree with the kind (adds or removes `bug-`), even when the front-matter value is already right; this is the repair `validate` points to. Nothing else renames a folder. Setting a field to its current value changes nothing and succeeds.

### `yardhand list [--status <name>] [--parent <id>] [--kind <kind>] [--priority <level>] [--size <size>] [--label <name>] [--assignee @handle] [--json]`

Read-only. Lists every issue in every status: priority, ID, kind, status, slug. Sorted `urgent`, `high`, `medium`, `low`, then no priority; within each, by ID (also the pickup order). `--parent <id>` lists all descendants by `parent:` (not the issue itself). `--label` matches issues that have that label. A missing `@` on `--assignee` is added. Filters combine with "and". `--json` prints every field, including `size`, `labels` and `effort`.

### `yardhand roadmap [--stdout]`

Writes `issues/ROADMAP.md`, a tree built from `parent:` fields: every issue, done ones checked `[x]`, `canceled` ones `[-]`, parents with an `N of M done` count of all descendants (canceled ones left out), and tags for `bug`, priority, the size of an open issue with no children, `N large left` on a parent with open large descendants, and any status other than `done`. The output has no dates, so `validate` can compare it with the file. `--stdout` prints it instead of writing.

### `yardhand release <semver> [--dry-run]`

Sets `released-in: <version>` on every issue in `done` that has none, and writes `issues/releases/<version>.md` (version, date, stamped issues grouped by top-level issue). Issues with an earlier version are not touched. Fails if that release file already exists. If an earlier run stamped issues but stopped before writing the release file, running the same version again rebuilds the file from the issues already stamped with it. A version lower than an existing release only warns. With nothing to release it prints so, writes nothing, and succeeds. `--dry-run` changes nothing. It does not run `git tag` or `npm version`.

### `yardhand validate [--json]`

Checks and reports every problem with its path, and keeps going after a problem; filesystem surprises (a file where a folder should be, an `ISSUE.md` that is a folder) are reported as problems, never thrown. A folder with a bad slug still takes part in every check. A folder with no recognizable ID still gets every check that does not need one: front matter, duplicate keys, `kind`, `status`, `released-in`, `size`, `labels`, `assignee`, `effort`, a required valid `id`, and that its `parent` exists. Messages name the file, the field and the fix in plain words, because people who never run the CLI may only see them as a failed CI check. Symlinks, entries that cannot be inspected, and leftover temp files are reported. Problems finding the root (for example an unreadable `issues/`) are reported as findings, not thrown. Exit code 1 if there is any error, 0 otherwise. Warnings print after the errors and never change the exit code.

Errors:

1. `yardhand.json` is valid (rules above). An invalid config is reported as a problem.
2. Every status has a folder. Every folder under `issues/` is a status, `releases`, or reported as unknown. The only loose files allowed in `issues/` are `yardhand.json` and `ROADMAP.md`; any other file is an error.
3. Every issue folder matches `<id>-[bug-]<slug>`, with a valid ID and slug. A second `bug-` is a reserved-prefix error.
4. Every issue folder contains `ISSUE.md` with valid front matter.
5. `id` equals the ID in the folder name.
6. `status` equals the folder's status.
7. `kind` is `feature`, `task` or `bug`.
8. `kind: bug` requires the `bug-` prefix, and the prefix requires `kind: bug`.
9. IDs are unique across all statuses.
10. `parent` exists. A level 1 issue omits the field entirely (an empty `parent:` is an error). For levels 2 and 3, `parent` is non-empty, exists, and has a shallower depth.
11. `released-in`, if set, is valid semver.
12. No key appears twice in the front matter.
13. `priority`, if set, is `urgent`, `high`, `medium`, or `low`.
14. Every ID in `depends-on` and `related` is valid, exists, and is not the issue itself.
15. `depends-on` has no loops.
16. `assignee`, if set, is a handle listed in `yardhand.json`, written in quotes.
17. `size`, if set, is `small`, `medium` or `large`.
18. Every label is lowercase kebab-case, listed in `yardhand.json`, and not repeated.
19. `effort`, if set, is one word (`^[a-z0-9][a-z0-9-]*$`).

Warnings:

- A slug longer than 40 characters (not counting `bug-`).
- `issues/ROADMAP.md` exists but no longer matches the issues: `ROADMAP.md is out of date, run yardhand roadmap.`
- `size` on an issue that has children.
- `size: large` on an issue not in `done` or `canceled`: consider splitting it.
- An issue in `done` with unchecked acceptance criteria (`- [ ]` followed by text, under `## Acceptance criteria`, outside code blocks).
- `effort` set when the assignee is blank or a person.
- AI is off (`"agents": []`) and an issue sets `effort` or is assigned to a model.
- `issues/` could ship: `package.json` has no `files` field and `.npmignore` has no `issues/` line; `package.json` `files` includes `issues/`; or a `Dockerfile` exists and `.dockerignore` has no `issues/` line. Only files at the repo root are checked. Hosting settings cannot be seen from the repo and are not checked.

`--json` prints `{ "ok": true|false, "errors": [...], "warnings": [...] }`, each entry having `path`, `rule` and `message`. A done issue without `released-in` is not flagged.

### Bare `yardhand`

With no command: if stdin and stdout are both a terminal and no `issues/yardhand.json` is found here or above, it runs the interactive `init`. In every other case (already set up, not a terminal, or a root that cannot be read) it prints the help. `--help`, `--version` and every explicit command are unchanged.

### Exit codes

0 success, 1 validation or usage error.

## AI tools

AI is optional. With `"agents": []` yardhand writes nothing about AI: no block, no skills, and no `effort` line in new issues. Everything else (statuses, IDs, `ready`, refinement, CI) works the same.

With one or more tools, `init` writes:

| Tool | Files |
|---|---|
| Any | The Yardhand block in `AGENTS.md` (created if missing) |
| Any | The skills in `.agents/skills/yardhand-<name>/SKILL.md` (the main copy) |
| Claude Code | An identical copy of the skills in `.claude/skills/yardhand-<name>/SKILL.md`, and `CLAUDE.md`: the block in an existing file, unless it already imports `AGENTS.md` with an `@AGENTS.md` line (then it is left alone, so the rules are not read twice); a missing file is created with just `@AGENTS.md` |

Codex reads `.agents/skills`, OpenCode reads `.agents/skills`, `.opencode/skills` and `.claude/skills`, and Claude Code reads `.claude/skills`. Most tools read `.agents/skills`, so that is the main copy; `.claude/skills` is a copy for Claude Code only. With Claude Code and OpenCode both picked, OpenCode sees each skill in both folders; the copies are identical.

The skills follow the Agent Skills format (front matter with `name` matching the folder, and `description`):

| Skill | Does |
|---|---|
| `yardhand-plan` | Turns a goal or bug report into level 1/2/3 issues with `new`. Writes no code. |
| `yardhand-refine` | Takes a `backlog` issue to `ready`: split, criteria, size, fields, `validate`, move. Writes no code. |
| `yardhand-build` | The "Picking up work" steps. |
| `yardhand-review` | Checks the change against the acceptance criteria. Never reviews an issue it built. On failure, adds `## Review notes` and moves the issue back to `in-progress`. |

Each skill says to use the CLI when the repo has it and to follow the block's rules by hand otherwise. The files are generated from one template and the CLI version, are plain copies (not symlinks), and carry a `<!-- Generated by yardhand ... -->` line. `init` only replaces or removes files with that line: a hand-written file at the same path is left alone and reported. When a tool is dropped (edit `agents`, run `init --force`), the generated skills in `.claude/skills` are removed when Claude Code is dropped, and both copies when AI is turned off, and folders left empty go with them. Blocks already in `AGENTS.md` or `CLAUDE.md` are never removed.

**Existing instructions.** The block covers issue tracking only, and says so in its first line: for anything else, the rest of the file wins. Where both cover the same thing, the repo's rule wins: branches are named `<id>-<slug>` unless the repo has its own branch naming rule, in which case that rule is followed and the issue ID goes in the branch name. After writing, `init` prints a warning for each line outside the block in `AGENTS.md` or `CLAUDE.md` that names another tracker (Linear, Jira, GitHub Issues, Asana, Trello, Shortcut) or a branch naming rule. It never changes those lines.

## Generated block in AGENTS.md

Written between markers so `init` can update it:

```
<!-- yardhand:start -->
## Work items (Yardhand)
...
<!-- yardhand:end -->
```

Content outside the markers is kept byte for byte, including when the block is appended and including bytes that are not valid UTF-8. Markers are found by plain text search anywhere in the file, so do not put the literal marker lines in your own text (for example in a fenced example); a pair there would be treated as the block. If the markers are damaged (one missing, reversed, or repeated), `init` fails and changes nothing, and it checks this before writing anything else. The block is generated from `yardhand.json` and the CLI version. It states: that it covers issue tracking only and the rest of the file wins for anything else; where issues live; the status words in order; the ID rules; use the commands for IDs, status changes and front matter, or follow the rules exactly by hand; the commands to use (`new`, `move`, `set`, `list`, `roadmap`, `release`); the field rules; the "Picking up work" convention; the skills and where they are; run `yardhand validate` before finishing; and the vocabulary mapping for Depot (level 1 is what Depot's skills call an epic, level 3 is a work item). Content outside the markers is never touched.

## Name constants

The tool name, config filename, issues folder name, issue filename, roadmap filename, releases folder name, and block markers are defined in one file (`src/names.ts`). Every message and the generated block use those constants, so a rename is a one-place change.

## Out of v1

`status add|rename|remove`, the frontend, a dev-dependency prompt, `validate --fix`, single-issue `validate`, and `run` (an optional command that would follow "Picking up work" and launch the assigned model with its `run` template).

## Picking up work

The same steps for a person, a model, a script, or a future `run` command:

1. Take an issue from `ready` whose `depends-on` issues are all `done`. Highest priority first, then lowest ID.
2. Claim it: move it to `in-progress` and set `assignee` to yourself.
3. Build it on a branch named `<id>-<slug>`. If the repo has its own branch naming rule, follow it and put the issue ID in the branch name.
4. Tick the acceptance criteria, then move it to `review` if that status exists, else `done`.

Nothing starts a build automatically. Moving an issue to `in-progress` claims it; it never launches anything.

## CLI behavior

- Unknown options and extra arguments are errors for every command. `--help` and `--version` accept no extra arguments. `<command> --help` prints that command's usage and accepts nothing else after it.
- Errors go to stderr, results to stdout, exit code 1 on failure. Output is written before the process ends, so a slow reader still receives every line.
- Paths in output always use forward slashes.
