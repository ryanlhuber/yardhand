# Yardhand spec (v1)

Yardhand is a file-based issue tracker that lives in a repo. Status is a folder, an issue is a folder, and the rules are mechanical so a script or a model can follow them. This file is the source of truth. Code and tests follow it.

## Layout

```
issues/
  yardhand.json
  backlog/
    017-add-auth/
      ISSUE.md
      notes.md
  in-progress/
  done/
```

- `issues/` is at the repo root. `yardhand.json` lives inside it.
- Each status in `yardhand.json` has a folder of the same name.
- Each issue is a folder named `<id>-<slug>/`, or `<id>-bug-<slug>/` for a bug, that contains `ISSUE.md` and any reference files.
- `issues/ROADMAP.md` (generated) and `issues/releases/<version>.md` (generated by `release`) are the only other things `issues/` may hold.
- Reference files inside an issue use relative paths or the issue ID. Never hardcode `issues/<status>/...`.

## yardhand.json

```json
{ "statuses": ["backlog", "in-progress", "done"] }
```

- `statuses` is an ordered list. It is the only source of truth for which statuses exist.
- The first status is where new issues start.
- `backlog` and `done` are required. Neither has to be first or last: any status can sit before `backlog` (for example `triage`) or after `done` (for example `canceled`).
- Status names are lowercase kebab-case: `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`. The interactive commands accept free-form names and normalize them (see "Names typed by people"); the file itself is strict.
- Names are unique. `releases` is reserved and cannot be a status.

## IDs

- Three levels at most: `017`, `017.01`, `017.01.01`.
- Level 1 is three digits. Levels 2 and 3 are two digits and start at `01`. Regex: `^\d{3}(\.(0[1-9]|[1-9]\d)){0,2}$`.
- No zero segments below level 1. `017` is valid, `017.00` and `017.00.00` are not.
- `000` is the catch-all for maintenance and bugs with no clear home. It is a normal level-1 ID.
- IDs are permanent and never reused, including after an issue is done.
- Allocation: scan every status folder. The next level-1 ID is the highest existing level-1 number plus one. The next child of a parent is the highest existing child number of that parent plus one. Level-1 numbers go up to 999, children up to 99. Allocation fails when full.
- The scan matches on separators: folder name must start with the ID followed by `-` (`017-`). Never match by prefix alone, so `017` never matches `0170`.
- Models never invent IDs. They call `yardhand new`.

## Slugs and the `bug-` prefix

- Lowercase kebab-case, verb first, for example `add-auth`.
- Regex: `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`.
- Slugs may change. The ID is the key. A rename changes the folder name only.
- `bug-` is the only reserved prefix. It appears only right after the ID and means `kind: bug`. After it, describe the symptom (`bug-login-redirect-loop`). `fix-` is not reserved. No other slug may start with `bug-`.
- The tool adds the prefix. Priority is not in the folder name, so changing it never renames a folder.
- A slug longer than 40 characters (not counting `bug-`) is a warning.

## Names typed by people

`init` (custom statuses), `new` (the slug), `move` and `list` (status names) normalize what is typed: trim, lowercase, and turn spaces and underscores into a dash. `Review 1` becomes `review-1`, and the result is shown. What is stored on disk is always the strict form.

## ISSUE.md

```
---
id: 017.01.01
kind: task
parent: 017.01
status: backlog
priority:
depends-on:
related:
assignee:
released-in:
---

## Description
<!-- What and why. A buildable unit should fit one model session. -->

## Acceptance criteria
<!-- Checkable outcomes, one per line. -->
```

- `id`: required. Must equal the ID in the folder name.
- `kind`: required: `feature`, `task` or `bug`. `new` defaults to `feature` at level 1 and `task` below. `kind: bug` and the `bug-` folder prefix must agree.
- `parent`: required for levels 2 and 3 and must be the ID with its last segment removed. Omitted for level 1. See "Moving work to a different parent" for the one exception.
- `status`: required. Must equal the name of the status folder the issue is in.
- `priority`: optional. One of `urgent`, `high`, `medium`, `low`. Empty means no priority. Front matter only; never part of the folder name.
- `depends-on`: optional. A comma-separated list of issue IDs that must be finished first, for example `017.02, 017.03`. The link is stored on the dependent issue only; there is no reverse field. A `depends-on` loop (A needs B and B needs A) is an error.
- `related`: optional. A comma-separated list of issue IDs that are linked but do not block this issue. Related links may point both ways.
- Blank means unset for every optional field. The template writes them all, blank. Only `parent` is omitted, for level 1.
- `assignee`: optional single-line text. `yardhand new` and `set` reject an assignee that contains a control character (C0, DEL, or C1, a newline or tab included), a Unicode line or paragraph separator (U+2028, U+2029), or `#`. The check is on the value as given, before any trimming; surrounding spaces are then trimmed.
- `released-in`: optional semver (the grammar at semver.org: no leading zeros, no empty identifiers), set by `yardhand release` when shipped.
- Front matter is a simple `key: value` block between `---` lines. A comment starts with `#` at the start of a value or after whitespace; a `#` inside a word is part of the value. No nesting. A key may appear only once. Both LF and CRLF line endings are accepted.

### Moving work to a different parent

The folder name and ID never change. Update `parent:` to the new parent. `parent:` is the source of truth for rollup, so after such a move it may differ from the ID prefix. `validate` accepts a different `parent` only if that parent exists.

## Commands

All commands, `init` included, run from the repo root or any folder below it. Yardhand finds `issues/yardhand.json` by walking upward. `init` in an already-initialized repo fails (even from a subfolder), and with `--force` it works on the existing root.

`new`, `move`, `set`, `roadmap`, `release` and `init` take an exclusive lock (`issues/.yardhand-lock`, a folder created atomically that holds the owner's process ID and a random token), so concurrent runs cannot allocate the same ID. A lock is abandoned only when the process that took it is no longer running, or, if it never wrote an owner, after 2 seconds. A slow but live holder is never evicted, however long it holds. Removing an abandoned lock is serialized by a second short-lived mutex (`issues/.yardhand-lock.reclaim`). Under it, the lock is re-read and removed only if it is still the same lock (same token) and its owner is still gone; while a lock folder exists nobody else can create one, so this cannot race with a new holder. A reclaim mutex older than 5 seconds belongs to a reclaimer that died and is cleared. A lock is released only by its owner, and a failure to remove it never hides the result of the work. A command waits up to 10 seconds for the lock (override with `YARDHAND_LOCK_TIMEOUT_MS`), then fails with a message. Folders under `issues/` that start with `.` are tool internals and are ignored.

`new`, `move`, `set`, `release` and `init` first need a complete view of every existing ID, so they refuse to run when: a status path is a file or cannot be listed; any entry cannot be inspected (permissions or I/O errors are never read as "absent"); a folder under `issues/` that is not a status holds, or may hold, issue folders; or there are symlinks. Yardhand never follows symlinks: `issues/` itself, status folders, issue folders, and `ISSUE.md` are checked. Reference files inside an issue folder are the user's and are not inspected.

`move` and `set` (and `release`, which never moves a folder) write the new `ISSUE.md` to a temp file in the issue folder first (a random name, `.ISSUE.md.<random>.tmp`, created exclusively, so nothing at a guessable path is ever written through), so a failed or partial write can only damage the temp file. If the folder has to move (a status change, or a `kind` change that adds or removes `bug-`), it then renames the folder, and renames the temp file over `ISSUE.md` (an atomic replace). If that last step fails, it renames the folder back, so the folder and the fields never disagree. The cases it cannot repair are a failure of the move-back itself, which it reports with exactly what state the issue is in, and a crash between the two renames, which leaves a status mismatch plus a temp file. `validate` reports both, and the temp file's message says how to finish or undo the change. If the status folder is missing, `move` creates it.

### `yardhand init`

Interactive by default, in a terminal:

1. **Pick statuses.** A space-bar checklist: `triage`, `todo`, `in-progress` (pre-checked), `review`, `merge-ready`, `blocked`, `canceled`, and "Add custom statuses...". `backlog` and `done` are always included.
2. **Custom statuses** (only if chosen). Free-form names separated by commas (semicolons also work), normalized (`Review 1` becomes `review-1`), shown as `Creating: ...`. Empty names, duplicates, `backlog`, `done`, `releases` and names with other characters are rejected.
3. **Order** (only with four or more statuses). A numbered list; nothing is pinned. Up/Down moves the cursor, space grabs or drops a status, while grabbed Up/Down moves it and a digit key (1-9) jumps it to that slot, Enter confirms. The starting order is `triage`, `backlog`, `todo`, `in-progress`, `review`, `merge-ready`, `blocked`, `done`, `canceled`, then custom statuses in the order typed.
4. **Create** everything and print the final order.

Non-interactive: `yardhand init --yes [--statuses a,b,c]`. Defaults to `backlog,in-progress,done`. `--statuses` is taken as the order and must already be valid (no normalization).

Creates `issues/`, `issues/yardhand.json`, and one folder per status (with a `.gitkeep` in each empty one). Creates the catch-all `000-maintain-repo` issue in `backlog` (even when another status comes first), so `000.NN` children (maintenance, bugs with no clear home) have a parent. Adds or updates the Yardhand block in `AGENTS.md`, and in `CLAUDE.md` if that file exists. Prints the Depot install command as a suggestion. Never runs it. Refuses to overwrite an existing `yardhand.json` unless `--force`. It takes the same lock as `new` and `move`, and runs the same completeness check, so a status list that omits a folder holding issues, or a tree it cannot fully read, is refused before anything is written. The catch-all is created with exclusive operations and is never overwritten. If `issues/` exists but cannot be read, `init` fails; it only starts fresh when nothing is set up. It validates `--statuses` even when it is empty.

### `yardhand new <slug> [--parent <id>] [--kind feature|task|bug] [--priority urgent|high|medium|low] [--depends-on <ids>] [--related <ids>] [--assignee <name>]`

Allocates the next ID, creates `issues/<first-status>/<id>-[bug-]<slug>/ISSUE.md` from the template, and prints the ID, the path, and a summary line (kind, priority, parent, status). The slug is normalized. A leading `bug-` in the slug becomes `--kind bug`, and the output says so; it fails if `--kind` says otherwise. Without `--kind`, level 1 is a `feature` and deeper levels are `task`. With no `--parent` it creates a level-1 issue. Fails if the parent does not exist or the parent is already level 3. `--depends-on` and `--related` take comma-separated IDs, and every ID must already exist. `new` builds the issue folder under a temporary `.new-*.tmp` name and renames it into place, so a failed `new` leaves nothing behind.

### `yardhand move <id> <status>`

Moves the issue folder to the status folder and rewrites `status:` in `ISSUE.md`. The status name is normalized. Fails if the status is not in `yardhand.json`, the ID is not found, or the destination already holds a folder with that name. Moving to the current status changes nothing and succeeds. Children (by `parent:`) are never moved; the output lists them. The folder name, `bug-` prefix included, is kept.

### `yardhand set <id> [--kind ...] [--priority urgent|high|medium|low|none] [--parent <id>] [--depends-on <ids>|none] [--related <ids>|none] [--assignee <name>|none] [--released-in <semver>|none]`

Changes fields on an existing issue. At least one flag is required. A value replaces the old one and `none` clears the field. `id` and `status` cannot be set (use `move`). Every change is validated before anything is written: IDs must exist, `parent` must be shallower than the issue (and a level-1 issue has none), `depends-on` cannot create a loop, `released-in` must be semver. Passing `--kind` also makes the folder name agree with the kind (adds or removes `bug-`), even when the front-matter value is already right; this is the repair `validate` points to. Nothing else renames a folder. Setting a field to its current value changes nothing and succeeds.

### `yardhand list [--status <name>] [--parent <id>] [--kind <kind>] [--priority <level>] [--json]`

Read-only. Lists every issue in every status: priority, ID, kind, status, slug. Sorted `urgent`, `high`, `medium`, `low`, then no priority; within each, by ID. `--parent <id>` lists all descendants by `parent:` (not the issue itself). Filters combine with "and". `--json` prints every field.

### `yardhand roadmap [--stdout]`

Writes `issues/ROADMAP.md`, a tree built from `parent:` fields: every issue, done ones checked `[x]`, `canceled` ones `[-]`, parents with an `N of M done` count of all descendants (canceled ones left out), and tags for `bug`, priority, and any status other than `done`. The output has no dates, so `validate` can compare it with the file. `--stdout` prints it instead of writing.

### `yardhand release <semver> [--dry-run]`

Sets `released-in: <version>` on every issue in `done` that has none, and writes `issues/releases/<version>.md` (version, date, stamped issues grouped by top-level issue). Issues with an earlier version are not touched. Fails if that release file already exists. If an earlier run stamped issues but stopped before writing the release file, running the same version again rebuilds the file from the issues already stamped with it. A version lower than an existing release only warns. With nothing to release it prints so, writes nothing, and succeeds. `--dry-run` changes nothing. It does not run `git tag` or `npm version`.

### `yardhand validate [--json]`

Checks and reports every problem with its path, and keeps going after a problem; filesystem surprises (a file where a folder should be, an `ISSUE.md` that is a folder) are reported as problems, never thrown. A folder with a bad slug still takes part in every check. A folder with no recognizable ID still gets every check that does not need one: front matter, duplicate keys, `kind`, `status`, `released-in`, a required valid `id`, and that its `parent` exists. Symlinks, entries that cannot be inspected, and leftover temp files are reported. Problems finding the root (for example an unreadable `issues/`) are reported as findings, not thrown. Exit code 1 if there is any error, 0 otherwise. Warnings print after the errors and never change the exit code.

Errors:

1. `yardhand.json` is valid (rules above). An invalid config is reported as a problem.
2. Every status has a folder. Every folder under `issues/` is a status, `releases`, or reported as unknown. The only loose files allowed in `issues/` are `yardhand.json` and `ROADMAP.md`; any other file is an error.
3. Every issue folder matches `<id>-[bug-]<slug>`, with a valid ID and slug. A second `bug-` is a reserved-prefix error.
4. Every issue folder contains `ISSUE.md` with valid front matter.
5. `id` equals the ID in the folder name.
6. `status` equals the folder's status.
7. `kind` is `feature`, `task` or `bug`.
8. `kind: bug` requires the `bug-` prefix, and the prefix requires `kind: bug`.
9. IDs are unique across all statuses.
10. `parent` exists. A level 1 issue omits the field entirely (an empty `parent:` is an error). For levels 2 and 3, `parent` is non-empty, exists, and has a shallower depth.
11. `released-in`, if set, is valid semver.
12. No key appears twice in the front matter.
13. `priority`, if set, is `urgent`, `high`, `medium`, or `low`.
14. Every ID in `depends-on` and `related` is valid, exists, and is not the issue itself.
15. `depends-on` has no loops.
16. `assignee`, if set, is a single line with no `#` or control characters (the same rule `new` and `set` enforce).

Warnings:

- A slug longer than 40 characters (not counting `bug-`).
- `issues/ROADMAP.md` exists but no longer matches the issues: `ROADMAP.md is out of date, run yardhand roadmap.`

`--json` prints `{ "ok": true|false, "errors": [...], "warnings": [...] }`, each entry having `path`, `rule` and `message`. A done issue without `released-in` is not flagged.

### Exit codes

0 success, 1 validation or usage error.

## Generated block in AGENTS.md

Written between markers so `init` can update it:

```
<!-- yardhand:start -->
## Work items (Yardhand)
...
<!-- yardhand:end -->
```

Content outside the markers is kept byte for byte, including when the block is appended and including bytes that are not valid UTF-8. Markers are found by plain text search anywhere in the file, so do not put the literal marker lines in your own text (for example in a fenced example); a pair there would be treated as the block. If the markers are damaged (one missing, reversed, or repeated), `init` fails and changes nothing, and it checks this before writing anything else. The block is generated from `yardhand.json` and the CLI version. It states: where issues live; the status words in order; the ID rules; never invent IDs, move folders or edit front matter by hand; the commands to use (`new`, `move`, `set`, `list`, `roadmap`, `release`); run `yardhand validate` before finishing; and the vocabulary mapping for Depot (level 1 is what Depot's skills call an epic, level 3 is a work item). Content outside the markers is never touched.

## Name constants

The tool name, config filename, issues folder name, issue filename, roadmap filename, releases folder name, and block markers are defined in one file (`src/names.ts`). Every message and the generated block use those constants, so a rename is a one-place change.

## Out of v1

`status add|rename|remove`, the frontend, a dev-dependency prompt, a harness picker, `validate --fix`, single-issue `validate`.

## CLI behavior

- Unknown options and extra arguments are errors for every command. `--help` and `--version` accept no extra arguments. `<command> --help` prints that command's usage and accepts nothing else after it.
- Errors go to stderr, results to stdout, exit code 1 on failure. Output is written before the process ends, so a slow reader still receives every line.
- Paths in output always use forward slashes.
